# HCP-0001 — Human Context Protocol: Founding Specification

**Status:** Draft  
**Version:** 0.1  
**Category:** Foundational / Standards Track  
**Date:** 2026-09-11

## Abstract

The Human Context Protocol (HCP) is a proposed open protocol for representing
personal context in a human-owned, portable, version-controlled, machine-readable
form.

HCP defines a conceptual and technical foundation for a personal Codex: a
collection of assertions about a human's identity, values, beliefs, preferences,
relationships, experiences, goals, boundaries, and other context that the human
chooses to make available to AI systems.

The canonical representation is human-readable Markdown with structured
metadata. Git is treated as a first-class mechanism for history, evolution,
diffs, rollback, and provenance. Machine-readable representations such as JSON
are derived from the canonical repository.

A core principle is the separation of human authority from AI inference. AI
systems may propose observations, but observations do not become authoritative
without an explicit human decision.

HCP also defines the conceptual basis for selective disclosure, temporal
validity, provenance, privacy classification, cryptographic integrity, and
provider-independent AI integration.

This document is a foundation for subsequent HCP specifications.

---

## 1. Motivation

Current AI systems typically maintain context inside individual providers,
applications, conversations, or proprietary memory systems.

This creates several problems:

- context is fragmented across providers
- users cannot easily inspect everything an AI believes about them
- context portability is limited
- AI inference can be confused with user-authored truth
- identity is often treated as static
- sensitive information may be over-shared
- changing providers can mean rebuilding context from scratch

HCP reverses the ownership model:

> **The human owns the context. AI systems consume it.**

The AI provider should be an implementation detail rather than the owner of
the person's enduring context.

---

## 2. Design philosophy

HCP is guided by the following principles:

1. **Human ownership** — the human is the root authority for their Codex.
2. **Human readability** — the canonical representation remains understandable
   without HCP software.
3. **Machine interoperability** — software can parse, validate, transform, and
   exchange context.
4. **Explicit authority** — facts, beliefs, preferences, and AI observations
   have distinct epistemic and authority states.
5. **Temporal identity** — assertions can change over time without erasing
   historical truth.
6. **Selective disclosure** — only the necessary context should be shared.
7. **Privacy by architecture** — sensitive data should be isolated and
   permissioned.
8. **Provider independence** — no AI vendor should be required.
9. **Auditability** — important changes and observations should be traceable.
10. **Reversibility** — human decisions should be reviewable and reversible.
11. **Extensibility** — new assertion types and integrations must be possible.
12. **No silent identity mutation** — AI systems cannot silently rewrite the
    human's canonical identity.

---

## 3. What HCP is not

HCP is not:

- an AI model
- a chatbot
- a proprietary AI memory database
- a psychological diagnosis
- a personality test
- a digital clone
- a social network
- a blockchain identity system
- a credential or password manager

HCP does not require blockchain, decentralized identifiers, or any particular
cloud provider.

---

## 4. Core concepts

### 4.1 Codex

A **Codex** is a human-owned repository containing structured and unstructured
personal context.

### 4.2 Assertion

An **Assertion** is a statement represented by a Codex. Assertions have a type,
authority, provenance, status, and potentially temporal validity.

### 4.3 Source

The **Source** identifies where an assertion originated, such as:

- human
- AI
- imported document
- external system
- derived assertion

### 4.4 Authority

Authority describes who or what is allowed to establish an assertion as
authoritative.

Human-authored assertions may be authoritative. AI observations are normally
proposals until reviewed.

### 4.5 Observation

An **Observation** is a statement proposed by an AI or another inference system.
It is explicitly non-authoritative until the human accepts or edits it.

### 4.6 Context Bundle

A **Context Bundle** is a purpose-specific subset of Codex content prepared for
disclosure to an AI system or other consumer.

### 4.7 Scope

A **Scope** defines which categories or assertions may be included in a Context
Bundle.

### 4.8 Trust Covenant

The **Human–AI Trust Covenant** is a human-declared set of conditions for the
ethical use of a Context Bundle. HCP-0002 defines the Covenant. It complements
technical controls but cannot override a provider's contracts, infrastructure,
or applicable law.

## 5. Canonical repository model

A Codex may use a structure such as:

```text
my-codex/
├── manifest.yaml
├── README.md
├── constitution.md
├── soul.md
├── identity/
├── values/
├── worldview/
├── preferences/
├── relationships/
├── life/
└── ai/
```

Suggested semantic areas:

```text
identity/
  core.md
  contact.md
  biography.md

values/
  values.md
  ethics.md
  boundaries.md

worldview/
  beliefs.md
  philosophy.md
  politics.md

preferences/
  communication.md
  food.md
  interests.md
  aesthetics.md

relationships/
  family.md
  people.md

life/
  work.md
  ambitions.md
  goals.md
  projects.md

ai/
  observations.md
  questions.md
  rejected.md
```

This structure is a convention, not a requirement that every Codex contain
every file.

## 6. Canonical representation

Markdown is the canonical human-facing representation.

Structured metadata is represented using YAML frontmatter.

Example:

```yaml
---
hcp: "0.1"
id: "belief.ai.human-agency"
type: "belief"
source: "human"
authority: "authoritative"
status: "active"
confidence: 0.80
created: "2026-09-11"
updated: "2026-09-11"
valid_from: "2026-09-11"
valid_until: null
visibility: "private"
tags:
  - ai
  - human-agency
---

AI systems should strengthen human agency rather than quietly replace it.
```

JSON is a machine interchange representation derived from the canonical
repository.

## 7. Assertion types

Initial assertion types are:

- `fact`
- `belief`
- `value`
- `principle`
- `preference`
- `boundary`
- `goal`
- `aspiration`
- `identity`
- `relationship`
- `experience`
- `observation`

Implementations may introduce additional types through future specifications.

---

## 8. Epistemic and authority model

HCP distinguishes between the content of a statement and its authority.

A human can write:

```yaml
source: human
authority: authoritative
```

An AI-generated observation should normally be:

```yaml
source: ai
authority: proposed
status: pending
```

Possible lifecycle:

```text
AI inference
    │
    ▼
 proposed
    │
 ┌──┼─────────┐
 ▼  ▼         ▼
accept edit   reject
 │    │         │
 ▼    ▼         ▼
authoritative authoritative rejected
```

AI observations must never silently transition into authoritative identity.

---

## 9. Confidence

Confidence is optional metadata describing epistemic confidence.

It is not a probability that the statement is objectively true.

Recommended range:

```text
0.0 ≤ confidence ≤ 1.0
```

A human may omit confidence where it is not meaningful.

---

## 10. Temporal model

Assertions may contain:

- `created`
- `updated`
- `valid_from`
- `valid_until`
- `supersedes`

Historical assertions should normally be retained rather than overwritten when
the historical state is meaningful.

Example:

```text
belief.v1
   │
   └── superseded by ──► belief.v2
```

Git history additionally preserves the evolution of the repository itself.

---

## 11. Git as part of the data model

Git is not merely a backup mechanism.

It provides:

- history
- diffs
- rollback
- provenance
- branching
- merging
- offline operation

Branches can also represent hypothetical identity experiments.

For example:

```text
main
 ├── experiment/career-change
 ├── experiment/new-city
 └── future-self
```

A hypothetical branch must not silently modify the canonical identity.

---

## 12. Constitution

`constitution.md` defines human-authored rules for interpreting the Codex.

Typical rules include:

1. Human-authored assertions have priority over AI observations.
2. AI observations are hypotheses unless explicitly accepted.
3. Uncertainty must not be represented as certainty.
4. Restricted information must not be disclosed without authorization.
5. Conflicting assertions should be surfaced rather than silently resolved.
6. The newest valid assertion normally represents current context.
7. Historical assertions should remain available when they explain evolution.
8. AI systems must not infer sensitive attributes and present them as facts.

The Constitution is itself human-authored context and therefore versioned.

---

## 13. `soul.md`

HCP deliberately permits an unstructured `soul.md`.

A human is not reducible to a database schema.

`soul.md` may contain prose about:

- what matters
- how life feels
- recurring themes
- contradictions
- aspirations
- personal philosophy
- things that are difficult to formalize

The schema describes the Codex. It does not define the totality of the human.

---

## 14. Privacy classification

Suggested visibility classes:

- `public`
- `private`
- `sensitive`
- `restricted`

Implementations should treat these as disclosure controls, not as legal
classifications.

Contact information such as address, phone, and email should generally be
isolated into restricted scopes rather than included in ordinary AI context.

Credentials and secrets are explicitly out of scope.

---

## 15. Selective disclosure

An AI should receive only the context necessary for the requested purpose.

Conceptually:

```text
Codex
  │
  ├── scope: assistant
  ├── scope: career
  ├── scope: family
  ├── scope: food
  └── scope: restricted-contact
```

A Context Bundle should identify:

- bundle ID
- Codex ID
- HCP version
- purpose
- creation time
- expiration time
- scopes
- included assertions
- integrity metadata
- declared trust conditions (required by the HCP 0.1 Context Bundle schema)

Future specifications will define the precise wire format.

---

## 16. AI context requests

An AI may request additional context.

The request should contain:

- requested scope
- purpose
- requested duration
- justification

The human may:

- approve
- deny
- approve partially
- provide an answer without granting persistent access

There should be no unrestricted equivalent of:

```text
dump_everything()
```

---

## 17. AI observations

AI systems may return structured observations such as:

```yaml
id: "obs.2026-09-11.001"
type: "observation"
source: "ai"
authority: "proposed"
status: "pending"
confidence: 0.72
derived_from:
  - "chat/session/example"
claim: "The user appears to prefer direct, structured explanations."
```

The human reviews the proposal.

Possible outcomes:

- accept
- edit
- reject
- archive

Rejected observations may be retained for auditability if the user chooses.

---

## 18. Cryptographic integrity

Future versions may define signatures for:

- Codex manifests
- assertions
- Context Bundles
- synchronization events

Ed25519 is a plausible initial signature algorithm, but HCP-0001 does not mandate
a cryptographic implementation.

HCP should use established cryptographic primitives and must not invent
cryptography.

---

## 19. Encryption

A reference implementation should support local encryption and encrypted
transport where applicable.

Hosted synchronization should ideally use a design in which the service does
not require plaintext access to the user's Codex.

A likely architecture is envelope encryption with device-held keys and
server-side encrypted blobs.

Exact key-management semantics belong in a future security specification.

---

## 20. Local-first architecture

The first reference implementation should work without a hosted account.

Conceptually:

```text
filesystem
    │
    ▼
Codex repository
    │
    ├── parser
    ├── validator
    ├── index
    ├── JSON serializer
    └── bundle generator
             │
             ▼
        AI adapters
```

Cloud synchronization should be an optional layer, not a prerequisite.

---

## 21. Machine representation

The machine layer should expose a normalized JSON representation.

This allows:

- validation
- deterministic serialization
- API integration
- context bundle creation
- provider adapters
- test fixtures

The JSON model should not replace the human-readable Markdown model.

---

## 22. AI integration

HCP should support provider-neutral adapters.

Potential integrations include:

- ChatGPT
- Claude
- Gemini
- local LLMs
- Ollama
- Open WebUI
- LibreChat
- MCP-compatible agents

An adapter translates between HCP and the target system.

The Codex itself remains provider-independent.

---

## 23. Agent integration

A future HCP-aware agent interface may expose operations conceptually similar to:

```text
codex.get_identity(scope)
codex.get_preferences(scope)
codex.request_context(request)
codex.propose_observation(observation)
codex.list_observations()
codex.review_observation(id, decision)
```

There should be no unrestricted:

```text
codex.dump_everything()
```

Permissions should be explicit and auditable.

---

## 24. Security threat model

HCP should consider:

- unauthorized disclosure
- malicious AI systems
- prompt injection
- inference attacks
- provider compromise
- device compromise
- malicious synchronization services
- identity spoofing
- privilege escalation
- metadata leakage
- compromised adapters

Core defenses:

- least privilege
- explicit authorization
- local-first operation
- encryption
- cryptographic integrity
- human review
- auditability
- reversible decisions
- strict schema validation

---

## 25. AI is not identity authority

The fundamental trust boundary is:

```text
                    HUMAN
                      │
               root authority
                      │
                      ▼
                   CODEX
                      │
             selective disclosure
                      │
                      ▼
                  AI SYSTEM
                      │
                observations
                      │
                      ▼
               human review
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
        accept       edit        reject
```

The AI can be an excellent observer.

It is not the owner of the identity it observes.

---

## 26. Conflict resolution

When assertions conflict, implementations should not silently choose based only
on semantic similarity.

The system should consider:

1. authority
2. status
3. temporal validity
4. explicit supersession
5. provenance

If ambiguity remains, the conflict should be surfaced.

---

## 27. Personal context as a graph

Future HCP versions should support relationships between assertions:

- `supports`
- `contradicts`
- `supersedes`
- `derived_from`
- `related_to`
- `depends_on`

This allows a Codex to become a structured context graph while preserving the
human-readable repository.

---

## 28. Human Context Stack

HCP occupies a specific layer:

```text
┌───────────────────────────────────┐
│ AI models / agents                │
├───────────────────────────────────┤
│ Provider-specific AI memory/state │
├───────────────────────────────────┤
│ HCP — human-owned context         │
├───────────────────────────────────┤
│ Personal files / data             │
├───────────────────────────────────┤
│ Human life                        │
└───────────────────────────────────┘
```

HCP does not attempt to replace ordinary personal data stores.

It provides a durable semantic layer for context intentionally shared with AI.

---

## 29. Fundamental interaction model

The intended interaction is:

```text
human
  │
  │ defines context
  ▼
Codex
  │
  │ grants scoped context
  ▼
AI
  │
  │ proposes observations
  ▼
human
  │
  │ reviews
  ▼
Codex revision
```

This creates a feedback loop without surrendering authority.

---

## 30. Open standard strategy

The protocol should be developed as an open specification with:

- public schemas
- public test fixtures
- deterministic examples
- implementation-neutral semantics
- compatibility tests
- documented versioning

The protocol should outlive any individual implementation.

---

## 31. Relationship to AI memory

HCP and AI memory solve related but distinct problems.

**AI memory asks:**

> What does an AI system remember about this user?

**HCP asks:**

> What does this human choose to tell AI systems about themselves?

AI memory can exist inside a provider.

HCP exists independently of the provider.

A provider may choose to implement HCP, but HCP does not depend on provider
ownership.

---

## 32. Minimal Codex

A minimal valid Codex should eventually be possible with:

```text
manifest.yaml
constitution.md
soul.md
```

and a small number of assertions.

The protocol should not force users into a large questionnaire.

A practical initial Codex can start with:


The user can expand it gradually.

## 37. Foundational principles

If future specifications conflict with this document, the following principles
should be preserved unless HCP itself undergoes a deliberate major revision:

> **The human owns the context.**

> **AI inference is not human authority.**

> **Context should be portable.**

> **Disclosure should be selective.**

> **Identity can evolve.**

> **History should be preserved.**

> **Privacy should be structural, not merely contractual.**

---

## 38. Manifesto

AI should know us better without owning us more.

Our context should not be trapped inside individual AI providers.

Our beliefs should not become opaque model state.

Our preferences should not be inferred when we can state them.

Our history should not disappear when our opinions change.

Our private information should not become the default context for every task.

We should be able to change AI systems without rebuilding ourselves.

**The human should remain the source of authority about the human.**

---

## 39. Status

HCP-0001 is an experimental founding specification.

It intentionally leaves implementation details to subsequent specifications.

The next priority is to define the repository and assertion formats precisely
enough that independent implementations can create and validate the same Codex.
